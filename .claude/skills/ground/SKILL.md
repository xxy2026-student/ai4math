# /ground — 想法落地

输入：$ARGUMENTS

每个想法在 `ideas/<想法名>/` 下有独立工作区（结构复制 `ideas/_template/`）：

```
idea.md        想法书（含修订记录）
grounding.md   落地报告
map.md         本想法的文献地图
reviews/       审稿意见（/review 产出）
```

## 第零步：定名与查重

从输入提炼 kebab-case 短名，先列出 `ideas/` 现有目录对照：

- 有同名或含义相近的目录 → 问用户：是继续做那个想法（增量模式，读旧
  文件接着干），还是全新想法（换名）；
- 确认全新 → 名字经用户认可后建目录。**禁止不经确认覆盖已有想法。**

## 第一步：把想法写下来

- 增量模式：读 idea.md 直接进第二步；
- 新想法：与用户对话，按 `_template/idea.md` 结构写成 idea.md。追问要少
  而准（3~5 个问题）：核心现象是什么？谁在跟谁博弈、冲突/错位在哪？
  什么外生、什么内生？理想定理长什么样？
- 不求形式化，求要素清楚。

## 第二步：文献侦察（派 scholar）

- 从想法要素生成 3~5 条检索线，交给 **scholar** subagent；
- 单篇精读笔记写 `literature/papers/<bibkey>.md`——**全库共享**，一篇论文
  只精读一次，已有笔记的论文增量更新；
- 本想法的文献地图汇总到 `ideas/<想法名>/map.md`；
- 文献量大时分两轮：先 abstract 级扫描 10~20 篇定坐标，再挑 3~5 篇
  最近邻精读全文。

## 第三步：落地报告

写 `ideas/<想法名>/grounding.md`，核心是 **2~3 个候选形式化**，每个包含：

1. 模型要素草案（players、时序、信息结构、支付、解概念——到能交给
   modeler 的精度）；
2. 刻画了想法的哪部分、牺牲了哪部分；
3. 与最近邻文献 [bibkey] 的逐条假设差异——新颖性声明的雏形；
4. 技术可行性预判：像哪个已知模型，可借用什么证明技术，风险在哪。

若 scholar 发现想法已被做过大半，如实报告重合度与剩余空间。

## 第四步：用户拍板 → 交接

- 报告给用户，等用户选定（或修改）一个候选。建议先跑一轮 /review
  再进入形式化；
- 选定后派 **modeler** 写 `problems/<p>/model.md`，并在其中链接本想法的
  grounding.md 与 map.md。

纪律：候选形式化里引用的每篇文献必须在 `literature/papers/` 有笔记；
新颖性只能说「在检索范围内未见」，并附检索线清单。
